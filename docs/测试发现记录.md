# 测试发现记录

记录在搭建靶子与首次全量回归中真实发生的"期望与事实不符"。
每条都写明：现象、证据、定性、处置。

**定性沿用实习期的三分法**：配置问题 / 接口问题 / 符合基准（不算缺陷，但要产品确认口径）。
额外增加第四类：**测试期望错误**（我方用例写错了，不是被测系统的问题）。

## F-001 未启用伪静态时，接口返回 200 + HTML 首页

- **发现时间**：2026-09-22
- **现象**：`GET /wp-json/wc/v3/products` 返回 HTTP 200，但响应体是 74254 字节的 HTML 首页。
- **根因**：WordPress 固定链接为默认"朴素模式"（`permalink_structure` 为空），
  `/wp-json/...` 形式的路径未被路由，请求落到首页。
- **证据**：响应 `Content-Type: text/html`，长度 74254；改为 `/%postname%/` 并 flush 后，
  同一路径返回 `application/json` 且状态码为 401。
- **定性**：配置问题（环境搭建缺陷）
- **处置**：在启动步骤中加入固定链接设置；已写入 `docker/README.md`。
- **价值**：**只断言状态码的测试会把"路由未生效"误判为"功能正常"**——
  这条是"断言实现而非行为"的现场样本。

## F-002 WooCommerce API 密钥（ck_/cs_）在 HTTP 下必然 401

- **发现时间**：2026-09-22
- **现象**：用后台生成的合法 `ck_`/`cs_` 密钥访问 HTTP 站点，返回
  `{"code":"woocommerce_rest_cannot_view","data":{"status":401}}`。
- **根因**：读源码确认，`includes/class-wc-rest-authentication.php` 中：
  ```php
  if ( is_ssl() ) { $user_id = $this->perform_basic_authentication(); }
  ...
  return $this->perform_oauth_authentication();
  ```
  即**密钥认证只在 HTTPS 下执行**，HTTP 下退化为 OAuth 并以匿名身份请求。
- **证据**：源码行号（`authenticate()`）+ 实测 401 响应体。
- **定性**：符合基准（产品设计如此，不是缺陷）
- **处置**：本地与 CI 改用 **WordPress 应用密码**鉴权（走 `determine_current_user`
  提前完成认证）。实测：admin 应用密码 → 200；customer 应用密码 → 403。
  若将来要把密钥认证纳入回归，需要给靶子启用 HTTPS。

## F-003 订单对象没有顶层 `subtotal` 字段

- **发现时间**：2026-09-22
- **现象**：用例断言 `order["subtotal"]` 抛 `KeyError`。
- **事实**：订单顶层字段为 `total` / `discount_total` / `shipping_total` /
  `total_tax` / `cart_tax` / `prices_include_tax`；`subtotal` 只存在于 `line_items[]`。
- **定性**：**测试期望错误**（用例假设了不存在的字段）
- **处置**：勾稽改为基于行项目计算——
  `discount_total == Σline_items.subtotal − Σline_items.total`，
  以及 `total == Σline_items.total + shipping_total + total_tax`（限 `prices_include_tax=False`）。
- **价值**：金额勾稽必须建立在**已核实的真实字段**上，不能凭印象写断言。

## F-004 页码越界返回 200 + 空数组（而非 400）

- **发现时间**：2026-09-22
- **现象**：`GET /wp-json/wc/v3/products?per_page=1&page=99999` 返回 200，响应体 `[]`。
- **对照**：`per_page=101` 返回 400
  `{"code":"rest_invalid_param","message":"per_page must be between 1 (inclusive) and 100 (inclusive)"}`。
- **定性**：**测试期望错误**（越界页返回空数组是合理设计）
- **处置**：把断言改为"200 + 空数组"；`per_page` 上界的断言经实测成立，保留原样。

## F-005 `/wp-json/wp/v2/users` 对匿名请求开放

- **发现时间**：2026-09-22
- **现象**：匿名请求该接口返回 200，并可读到管理员账号的
  `id` / `name` / `slug` / `link` / `avatar_urls`。
- **定性**：**符合基准，待产品确认口径**。这是 WordPress 的默认行为
  （用于公开作者归档），不是配置错误，因此不作为缺陷上报。
- **处置**：保留一条用例固定当前行为——一旦站点收紧权限，该用例会失败并提醒更新结论。
- **风险提示**：若该站点对公网开放，用户枚举会成为后续攻击的信息基础，
  建议产品侧明确是否需要收敛。

# 附录：做 CI 门禁时，被自己的框架打脸两次

这两条不是被测系统的缺陷，是**框架自身**的问题。留档的原因一样：
它们都是"看着通过、其实没测到"的现场样本，正是 L3 要消灭的东西。

## B-001 「全部跳过」也是一种假绿

- **背景**：原来的 CI 文件已经写好，但靶子容器的启动步骤还是 TODO。
- **现象**：如果在那种状态下推送，`pytest -m smoke` 会因为靶子不可达
  **跳过全部用例并以退出码 0 结束**——GitHub Actions 显示一个绿色对勾。
- **本质**：门禁的信号来自"退出码"，而"跳过"的退出码也是 0。
  于是"成功"变成了"什么都没测"的同义词。
- **处置**：`ci` 环境设 `skip_when_unreachable: false`（不可达即失败），
  并加 `QAGATE_NO_SKIP=1`（出现任何跳过即判整次失败）。
- **实测对照**（2026-09-22，靶子故意指向不可达端口）：

| 配置 | 结果 | 退出码 |
|---|---|---|
| 无防线 | `24 skipped` | 0（假绿） |
| `QAGATE_NO_SKIP=1` | `24 skipped` + 门禁失败提示 | 1（正确阻断） |

## B-002 配置里的占位符会把「没用到的那部分」也算进去

- **背景**：为了让 CI 凭据不进仓库，配置支持 `${VAR}` 占位并从环境变量注入。
- **现象**：加了 `ci` 环境之后，**本地**回归也开始报
  `KeyError: 配置引用了未设置的环境变量 QAGATE_ADMIN_APP_PASSWORD`——
  因为加载器在选环境之前就把整份 YAML 的占位符全展开了。
- **本质**：加载顺序错误。未被选中的环境里的占位符，不该影响本次运行。
- **处置**：改成**只展开当前选中的环境**（以及顶层 `credentials`）。
  这个 bug 是"本地真跑一遍"才暴露的，只看代码是看不出来的。

> 这两条合起来正好回答一个面试问题：**你怎么知道你的门禁不是摆设？**
> 答案是——我给门禁做过**故意的失败注入**：把靶子指向一个死端口，
> 确认它真的会红。没被验证过的门禁和没有门禁是一样的。
